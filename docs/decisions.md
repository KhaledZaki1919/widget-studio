### ADR-001 — Product decisions from the brief (D1–D9)
**Status:** Accepted (2026-10-20).

- **D7** Arabic (default) + English, full RTL.
- **D8** No accounts, no sync, no analytics. Data stays in the App Group container.
- **D9** Bundle ID `com.khaled.widgetstudio`, widget `com.khaled.widgetstudio.widgets`, App Group `group.com.khaled.widgetstudio`.

Open questions use the brief's defaults: name "Widget Studio", Android after iOS ships, free, lock-screen widgets in v1.1.

### ADR-002 — Project generated by XcodeGen
**Status:** Accepted (2026-10-20).

### ADR-003 — Unsigned IPA from CI, ad-hoc signed for entitlements
**Status:** Accepted (2026-10-20). Same as Lakhas ADR-012.
**Decision:** CI builds Release for `iphoneos` with `CODE_SIGNING_ALLOWED=NO`, then `ios/scripts/build-ipa.sh` ad-hoc signs (`codesign --sign -`, no certificate, no secret) the widget extension first and then the app with their entitlements, so Sideloadly can see the requested App Group (and HealthKit). The script fails if either bundle lacks the App Group entitlement, if `UILaunchScreen` is missing, or if a secret-like string is in the bundle. The IPA is uploaded as artifact `WidgetStudio-ipa`, kept 30 days.

### ADR-004 — Runtime App Group resolution (free Apple ID fallbacks)
**Status:** Accepted (2026-10-20); behavior on device to be confirmed by the M0 Diagnostics report.
**Context:** In Lakhas, a free-Apple-ID Sideloadly install reported no App Group in the signing profile; Sideloadly lists custom entitlements as a paid feature. Signers that do support groups may rewrite the group ID.
**Decision:** Ported from Lakhas ADR-014. App and widget resolve the shared container at runtime:
1. `ALTAppGroups` from Info.plist. AltStore/SideStore register these groups on free accounts and rewrite the key to the real IDs when signing (added 2026-10-20, after the M0 device test);
2. App Groups in `embedded.mobileprovision` (as rewritten by the signer);
3. the compiled ID from Info.plist (`WSAppGroup`);
4. the target's own container (not shared). The widget then shows "Open the app to set up widgets".

The first candidate whose container is writable wins. `StoreLocation.source` records which step it came from. Diagnostics lists the resolved group, its source and every candidate tried; the check widget shows the group name.

Never hardcode the bundle ID, team prefix or group at runtime. No Keychain sharing: the widget never needs a key.
**If the App Group fails on device:** widgets can't read saved designs. Fallbacks to evaluate in M1/M3: bundle-only templates configured through the widget's AppIntent parameters (stored by the system, no App Group needed), and treating sideloaded builds as "templates only" until a paid account.

### ADR-005 — M0 capability probes (Diagnostics)
**Status:** Accepted (2026-10-20).
**Context:** The brief (§2) requires App Group, HealthKit, location in the widget and battery in the widget to be verified on a free-Apple-ID install before templates rely on them.
**Decision:**
- The widget extension writes a **widget report** (`Probe/widget-report.json`) on every timeline reload: heartbeat, whether it saw the app's heartbeat, `CLLocationManager.isAuthorizedForWidgetUpdates`, a location fix from inside the extension, and `UIDevice.batteryLevel`/state read inside the extension. The probe widget also shows these on the home screen, so they are visible even without a shared App Group.
- The app's hidden **Diagnostics** screen (long-press the version number in About; in M0 also a visible button) shows: build and profile info, App Group read/write, the widget report, location permission (When In Use, needed for `NSWidgetWantsLocation`), HealthKit (availability, authorization request, a steps query), app-side battery, and a shareable plain-text report.
- Each probe result is one of: ok, failed (with reason), not run.
- The app requests HealthKit read for step count and sleep analysis only (the bindings in brief §4.5).
- Outcomes go in a "Device findings" update of this ADR. Templates whose capability fails are dropped or rebound.

**Device findings (2026-10-20, M0 IPA, Sideloadly, free Apple ID):**
| Check | Result |
|---|---|
| Install, launch, widget in the gallery | ✅ the app installs; the widget appears and renders |
| Location inside the widget (`NSWidgetWantsLocation`) | ✅ fix received in the extension |
| Battery inside the widget | ✅ level readable in the extension |
| HealthKit | ✅ available in the app |
| Signing profile (`embedded.mobileprovision`) | ❌ **missing** in the installed bundle |
| App Group | ❌ **Shared ✕** in both the app and the widget: no group container is usable |

**Consequences:**
- Weather, prayer/Qibla, location and battery templates can work: the widget gets location and battery itself.
- Health templates can rely on HealthKit. Read access is a separate prompt, and a denial looks like "no data".
- **The app can't hand data to the widget on this install.** Saved designs, user photos, counters written by the app and the app's caches are invisible to the widget. M1 therefore renders **bundled specs** in the widget, chosen through the widget's AppIntent configuration, which the system stores without an App Group (see ADR-004). M3 has to design "My widgets" around this, or ship it only to installs where an App Group resolves.
- With no profile, the resolver only has the compiled ID and `ALTAppGroups` to try. AltStore/SideStore register `ALTAppGroups` on free accounts, so those installers may give a working group (ADR-004 order). Sideloadly with a free Apple ID doesn't.

### ADR-006 — Swift 5 language mode; CI compile-first, lint non-blocking
**Status:** Accepted (2026-10-20). Learned on Lakhas (ADR-019 there).
**Decision:**
- App, extension and `WidgetKitCore` build in Swift 5 language mode (`SWIFT_VERSION: 5.0`, `swiftLanguageModes: [.v5]`), minimal concurrency checking.

- Claude reads failures with `gh run view --log-failed` and fixes all errors from a run in one commit; waits are foreground and capped at 8 minutes, no background watchers.

### ADR-009 — Spec v1 implementation choices (M1)
**Status:** Accepted (2026-10-21).
- **Decoding vs. validation:** `WidgetSpec` decodes leniently (unknown keys ignored). Unknown layer types decode as `.unknown` and unknown enum values (family, action, …) fail decoding. `SpecValidator.validate(data:)` turns either into a `SpecIssue` with a JSON path (`layers[3].action: unknown value`), never a crash. Validation returns the spec with frames clamped to the canvas (`Result<WidgetSpec, SpecIssues>`).
- **AI mode:** `SpecValidator(mode: .ai)` also enforces brief §5.1 (only `open.app` buttons, only time/date/weather bindings, font size ≥ 11). The exported `Resources/Spec/widget-spec.v1.schema.json` describes structure only; a unit test keeps its enums in sync with the Swift whitelists.
- **Additions to the brief's spec** (all optional):
  - `analogClock.timezone` (a timezone field or IANA name) for world clocks;
  - `dotBars.offColor`;
  - `labels` as comma-separated text or a binding;
  - literal values for `ring.progress` (`"0.4"`), `dotBars.values` (`"0.2,0.5,1"`) and `dotGrid.values` (`"0110…"`).
- **Binding kinds:** each binding yields text, number, levels, date or symbol. The validator checks the kind where it matters: `ring` needs a number, `dotGrid`/`dotBars` levels, `live.target` a date, `icon` a symbol.
- **Digits:** all bindings use Latin digits (also in Arabic), so they suit the `dot` font and never mirror. Weekday and month names follow the language (`ar_EG@numbers=latn`).
- **RTL:** the canvas is always laid out left-to-right in canvas units. In Arabic, only layers with `mirror: true` move to the mirrored frame and lay out their content right-to-left. `forecastRow` runs right-to-left in Arabic.
- **Circle templates:** with `background.outerColor`, the widget is filled with the outer color and the background is drawn as the largest centered circle.
- **Fonts:**
  - Doto ships as a variable font (default instance Black); its weight is set on the `wght` axis through CoreText.
  - IBM Plex Sans Arabic ships four static weights (Regular, Medium, SemiBold, Bold).
  - Fonts are registered per process (app and extension) and ship with their OFL licenses.
- **Buttons** are `Link`s to `widgetstudio://action/<action>?spec=<id>&arg=<value>` until the interactive AppIntents arrive (M4).
- **Data:** M1 renders `DataSnapshot.sample` (Cairo); real providers replace it in M4.
- **Widget:** the spec widget uses `AppIntentConfiguration` to pick a **bundled** spec, because the App Group doesn't work on Sideloadly installs (ADR-005). Its timeline follows the spec's `refresh`, and content margins are disabled so the canvas fills the widget.

### ADR-010 — RTL without flipping, fonts through UIAppFonts, render tests (M1 device fixes)
**Status:** Accepted (2026-10-25). Fixes from the M1 device test.

**1. RTL**
- **Problem:** in Arabic, the gallery mirrored everything like an image: text, digits, clocks and the segmented control. Forcing `layoutDirection = .rightToLeft` on a `List` inside an LTR app makes its UIKit cells flip.
- **Rule:** nothing in a spec is ever flipped. `SpecView` lays out the canvas left-to-right and sets no direction per layer. In Arabic, a layer with `mirror: true`:
  - moves to the mirrored frame;
  - swaps its own alignment (leading ↔ trailing);
  - reverses its item order: forecast days, week bars and labels, calendar rows.

  Glyphs, digits and clock hands keep their shape. Mirroring a number's *position* is fine (the digital clock and the tasbeeh counter do it).
- **Arabic text:**
  - Field defaults and `dotBars.labels` may be `{en, ar}`.
  - Sample data has Arabic values.
  - Live texts get the spec's locale (`ar_EG@numbers=latn`) and time zone.
  - Tracking is ignored for Arabic text, because it breaks letter joining.
  - Number runs inside Arabic text are wrapped in LTR isolates (`BidiText`), so "33° / 21°" isn't reordered.
  - Date bindings print in the render's time zone.

**2. Widget showed only the redacted placeholder**
- **What was ruled out:** the IPA was inspected. The extension contained the package resource bundle and valid App Intents metadata.
- **What changed:** the renderer used fonts that only exist in-process:
  - Doto, registered at runtime with `CTFontManagerRegisterFontsForURL`;
  - a CoreText variation font (`Font(CTFont)` with a `wght` axis), created anew for every text in every entry (up to 60 entries).

  The usual way for widgets to get custom fonts is to bundle the files in the extension and declare them in `UIAppFonts`. A runtime-registered variable font may not survive WidgetKit's rendering, and per-entry instances strain the ~30 MB budget.
- **Fix:**
  - All fonts live in `ios/Fonts`, are bundled in the app **and** the extension, are declared in each `UIAppFonts`, and are referenced only by PostScript name.
  - Doto ships as three static instances (Regular 400, Bold 700, Black 900, ROND 0), built from the OFL variable font by the manual workflow `.github/workflows/fonts.yml` (fontTools). Doto has no Reserved Font Name. IBM Plex (RFN "Plex") ships unmodified.
  - `build-ipa.sh` fails if a bundle lacks a font it declares.
  - Formatters are cached, and the widget loads the specs once per process.
- **Not yet confirmed on device.** If the widget still shows the placeholder, read the extension's crash or memory report (Settings → Privacy & Security → Analytics & Improvements → Analytics Data → `WidgetStudioWidgets-…` or `JetsamEvent-…`).

**3. Render tests (app-hosted `WidgetStudioTests`, Simulator)**
- **RTL invariants, no references needed:**
  - Layers without `mirror` must render pixel-identically in English, in Arabic, and in Arabic inside an RTL host.
  - An Arabic render with `mirror` must equal an English render of the hand-mirrored spec.
- **Every test spec renders through `SpecWidgetContent`,** the widget's own view (moved into the package for this), in every size and both languages. The render must not be blank.
- **Snapshots:**
  - One reference PNG per spec and language, in `WidgetStudioTests/Snapshots`.
  - Renders use a fixed date (2026-10-21 14:05 Cairo), sample data and frozen live text.
  - Every render is uploaded as the `snapshots` artifact. A missing reference skips (recorded); a mismatch above 0.2 % of pixels fails and writes a diff image.

**4. Layout fixes**
- **World clocks:** the stray GMT offset is gone, and the steps grid is a real month calendar (`MonthGrid`: 7 columns from the calendar's first weekday, padding before day 1).
- **Forecast:** the icon no longer overlaps the temperature, and "°" is drawn in the system font inside dot text.

### ADR-011 — Template library (M2): spec extensions, sizes, widget picker
**Status:** Accepted (2026-10-25).
**Context:** TEMPLATES.md defines the Mono set. Several templates can't be expressed in the brief's spec v1:
- light/dark variants with an editable accent;
- the stopwatch's idle and running states;
- the next prayer column in red;
- the Qibla arrow;
- "today" in red on the month grid and the best night in red;
- user-picked tile icons;
- big-numeral countdowns.

**Decision: optional additions to spec v1** (existing specs stay valid; validator, schema export and tests updated):
- **Color tokens:** `@bg @fg @muted @accent @outer @line @dim @onAccent`. Values are the TEMPLATES.md style table plus `line`/`dim` for dividers and unlit dots. They resolve per theme (`WidgetSpec.resolvingTokens(theme:)`, an exact JSON round trip). `RenderContext.theme` overrides the spec's theme (detail previews, the widget's Appearance option). M3's accent editor will override `@accent`.
- **Layer `when`:** `"{{b}}"` (truthy), `"!{{b}}"` or `"{{b}} == value"`. Unknown or missing values are falsy.
- **Layer `rotation`:** degrees, a number or a number binding.
- **`highlightColor`:** on `dotGrid`, cells with level ≥ 2 (`MonthGrid` marks today with 2); on `dotBars`, the highest bar.
- **Field type `icon`:** whitelisted SF Symbols. Timezone defaults may be empty (= not set).
- **Bindings:** `steps.month`, `counter.progress` (counter ÷ the spec's `target` number field), `prayer.next.key`, `days.<dateField>` (whole days left; used for big dot countdowns, because a live timer would show "1639:12:33" for a date months away).
- **Top-level `category`:** time, weather, health, prayer, countdown, photo, tiles, counters. Template ids may be camelCase (TEMPLATES.md).
- **Arabic sizing:** Arabic text in a Latin family is set 1 pt larger (TEMPLATES.md: "Arabic labels: same sizes +1").
- **Icon whitelist:** `"bluetooth"` removed, because it isn't an SF Symbol and rendered empty. Tile symbols added (hotspot, dark mode, rotation lock, calculator, TV, NFC, …).

**Library:**
- 28 templates in `Resources/Templates/<id>.json`:
  - every template in TEMPLATES.md;
  - `mono.location.coords`, since location in the widget is verified (ADR-005).
- Focus Today and Stopwatch sit under Countdown (TEMPLATES.md "Focus & Countdown").
- Sample data until M4.
- The photo layers show a placeholder until M3 adds photo picking. The halftone filter is applied when saving (M3).
- Sleep Week shows day initials only; per-night durations need a second label row (later).

**Sizes:** a template is designed for one family. It also offers every larger family, scaled uniformly and centered, with the background filling the widget (`SpecFamily.supportedFamilies`). The detail screen previews each supported size in light and dark.

**Widget:**
- Kind `WidgetStudioSpec` is kept, so placed widgets survive.
- The `SelectTemplateIntent` picks any bundled template. Edit Widget groups templates by category (`IntentItemCollection` sections) and searches names in both languages (`EntityStringQuery`).
- An Appearance parameter: template default, match system, light or dark.
- Defaults per size: small `mono.clock.digital`, medium `mono.weather.forecast`, large `mono.prayer.day`.
- A template designed for a larger size than the widget is drawn shrunk; the picker can't filter by widget size.

**App:** Home is the Library. The M1 test designs moved into Diagnostics. The check widget stays in the bundle.

**Tests:**
- Package:
  - all 28 valid; ids = file names; catalog order;
  - bilingual names, labels and literal texts;
  - every visible binding resolves;
  - tokens resolve in both themes;
  - stopwatch and prayer-day conditions.
- App:
  - every template through `SpecWidgetContent` in each supported size, both languages and both themes;
  - a snapshot per template and language.

### ADR-012 — Gray template widgets: diagnosis tools, error text, one widget kind per size, signing diagnostics
**Status:** Accepted (2026-10-25). The cause is **not confirmed yet**; this build is meant to find it on the device.
**Context:**
- M2 device test, installed with Fast Store (a paid re-signing store; the owner's install method from now on).
- The template widgets stay a gray redacted placeholder. The check widget renders in the same install. No spec-rendered widget has ever rendered on the device.

**Evidence so far:**
- The gray medium widget shows the Forecast template's real layout, redacted.
- So `placeholder(in:)` ran in the extension: the template library loads from the package bundle, the JSON decodes, and `SpecView` builds its whole view tree.
- What never arrives is a real (unredacted) entry. That leaves:
  1. the AppIntent snapshot/timeline path not delivering;
  2. unredacted text failing (fonts; redaction hides text, so it would hide a font problem);
  3. a crash, timeout or memory kill while building or rendering the real entry.

The M2 build made the following suspects unlikely but not impossible:
- entry count (Forecast and Steps refresh hourly: one entry);
- missing resources (inspected in the IPA).

**Decision:**
1. **Find the cause on the device:**
   - **Step log:** `WidgetLog` records every template-widget step (placeholder, snapshot, timeline start/end with duration, free memory and entry count, render) in the extension's container. The **large check widget** shows the last lines; it uses system fonts only and renders on this install.
   - **Comparison widgets:**
     - **Test · Fonts** draws only the bundled fonts and says whether each is registered in the extension.
     - **Test · Template** renders a template through the same renderer with `StaticConfiguration`, with no AppIntent and no entity query.
   - **Reading the result:**
     - both render, but the template widgets stay gray → AppIntent path;
     - Test · Template is gray too → renderer;
     - Test · Fonts fails → fonts.
   - Timelines load only the selected template file (`TemplateLibrary.load(id:)`), not all 28.
2. **No silent gray:** a missing, invalid or oversized template renders as plain system text with the reason (`WidgetProblemView`). Crashes and memory kills can't be caught in code; the step log shows where they happen.
3. **One widget kind per size:** `WidgetStudioSmall`, `WidgetStudioMedium`, `WidgetStudioLarge`. Each has its own intent and entity query that lists only templates that fit: same size or smaller, never shrunk. Grouped by category and searchable. Size-specific queries need separate entity types, because the query can't see the widget's family. The M1/M2 kind `WidgetStudioSpec` is removed; placed widgets must be re-added.
4. **Signing diagnostics:** Diagnostics shows, for the app **and every extension**:
   - the embedded profile (name, team, expiry, App Groups, entitlements);
   - what is actually signed into the executable, read from the Mach-O code signature: CodeDirectory identifier and team, ad-hoc flag, and the signed entitlements (App Groups, application-identifier). This works even when a store ships no readable profile.

**Build rule:**
- Each fix is pushed with compile + unit tests only.
- `[full]` runs the Simulator tests.
- One IPA with `[ipa]` after all fixes are green (CLAUDE.md).

**Next:** the owner's screenshots of the check widget (large), Test · Fonts, Test · Template and Diagnostics → Signing decide the real fix. The test widgets are removed once it is solved.

### ADR-013 — Template widgets use StaticConfiguration (one widget per template)
**Status:** Accepted (2026-10-25). Supersedes the AppIntent part of ADR-011/ADR-012.

**Context: the M2 device test on the owner's Fast Store install.**
- **Test · Template** (`StaticConfiguration`) renders a template correctly in small and medium. It uses the same bundled files, renderer, fonts, entry view and memory profile.
- Every **AppIntentConfiguration** widget stays a gray placeholder, even as a gallery preview before a template is picked. No error text ever appears.
- The IPA's extension contains a correct `Metadata.appintents`: 3 intents, 3 entities, 3 queries, the Appearance enum, the right parameter types.

**Diagnosis:**
- Our AppIntent snapshot does exactly the static widget's work for the default configuration.
- What differs is the system's App Intents machinery: configuration storage, intent instantiation, entity resolution. On this install, that machinery never delivers our entry to the screen.
- Re-signing by the store is the likely factor. This can't be fixed or verified from our code.

**Decision:**
- **One `StaticConfiguration` widget per template:** `TemplateWidget<ID>`, kind `WidgetStudio.<template id>`, in the template's own size only, so nothing is shrunk.
- **Picking:** the user swipes the widget gallery, which shows each real design with its name.
- **Identities:** `TemplateIDs` (WidgetKitCore) has one type per template, because a `Widget` must have `init()`. A unit test guarantees every library template has one.
- **Bundles:** category sub-bundles keep the widget bundle builder within 10 entries per block.
- **Kept:** the step log, the error text (ADR-012) and the check widget.
- **Removed:**
  - the AppIntent widgets (`WidgetStudioSmall/Medium/Large`) and their intents and entities;
  - the Test · Fonts / Test · Template widgets, since the real widgets now use the path Test · Template proved.

**Rejected alternatives:**
- **Legacy `IntentConfiguration` (`.intentdefinition`):** it rests on the same system intent infrastructure, so it would likely fail the same way. Dynamic lists also need a separate Intents extension, one more App ID for the store to sign.
- **One widget per category:** it still needs a configuration to choose within a category.

**Costs:**
- 28 entries in the widget gallery.
- No per-widget Appearance or search: each template uses its default theme.
- M3's "pick a saved design in the widget's edit menu" (brief §3) can't use this path on this install. M3 must design around it, e.g. a fixed number of "My widget 1…N" slots, each a static widget showing a design the app assigns, which needs the App Group. Decide in M3.

**Revisit:** for an App Store / normally provisioned build, test `AppIntentConfiguration` again (code in git history before this ADR).

### ADR-014 — No developer account until the end; M3 works inside the app; two build modes
**Status:** Accepted (2026-10-25), owner's decision.
**Context:**
- The owner installs with Fast Store and will not buy an Apple Developer account now.
- On that install there is no App Group (the app and the widget can't share files; ADR-005, ADR-012), and AppIntent-configured widgets never render (ADR-013).
- The account is bought once, near the end, to test and publish.

**Decision:**
- **M3 works fully inside the app:**
  - the editor;
  - My widgets: preview, rename, duplicate, edit, delete;
  - saved designs and photos.
- **All storage goes through one `SharedStore`:** the App Group container when the resolver finds one, else the app's own container. When the App Group starts working (own account), the same code shares designs with the widget; nothing is rewritten.
- **Two build modes, chosen by a compile flag** (`WS_EXTRA_CONDITIONS` build setting → Swift condition `WS_DEVELOPER`):
  - **store mode** (default; what CI builds and ships as the IPA):
    - the 28 fixed template widgets (ADR-013);
    - one **My widget** per size that reads saved designs from `SharedStore`. Without an App Group it shows "Saved designs appear here in the App Store version" (ar/en), never gray.
  - **developer mode** (later, own account):
    - the configurable widget restored from before ADR-013 (commit `997651a`);
    - Edit Widget picks any saved design or template, with Appearance and search.
- **CI** compiles both modes on every push and runs the unit tests (the package has no mode switch; the modes differ only in the app and extension). The IPA is built in store mode only, and only `WidgetStudio.ipa` (the no-HealthKit fallback is dropped: HealthKit installs fine with Fast Store).

### ADR-015 — Saved designs, SharedStore, editor rules (M3)
**Status:** Accepted (2026-10-25).

**A saved design** (`SavedDesign`) keeps:
- a **copy of the template spec** at save time, so library updates never change a saved design;
- the user's **field values** (`LocalizedText`: text and city fields hold Arabic and English);
- an optional **theme**;
- **color overrides** for the tokens `accent`, `bg` and `fg`, applied on top of the theme (`resolvingTokens(theme:overrides:)`);
- the **photo's file name**.

Empty field values fall back to the template defaults.

**Storage:** `SharedStore` is the only storage for designs and photos:
- `Designs/designs.json` (newest first) and `Designs/Images/`;
- in the App Group container when the resolver finds one, else the app's own container;
- each photo save gets a fresh file name, and unused photos are removed after saves.

**Editor rules** (`DesignEditing`):
- **Links:** a `url` field accepts only http/https links (the spec rule "no remote URLs" still applies to every other text). Shortcut names can't be links.
- **Other fields:**
  - dates must parse;
  - time zones must exist (empty = not set);
  - icons come from the whitelist;
  - colors are hex.
- **Save** requires a non-empty name (≤ 60 characters), and the spec with the overrides must still validate.

**Photos:**
- Picked with PhotosPicker and redrawn upright (orientation applied).
- Cropped to fill (or fitted) at the image layer's pixel size (3×, longest side ≤ 1024), so the widget's ~30 MB budget is safe.
- `halftone` (Dot Portrait) and `mono` are applied once, when the photo is picked; the widget never filters. Halftone and mono photos are stored as PNG, others as JPEG.

**Tabs:** Templates and My widgets. Save switches to My widgets. Without an App Group, My widgets explains that the home screen shows saved designs in the App Store version (ADR-014).

### ADR-016 — Real data in the widget without an App Group (M4)
**Status:** Accepted (2026-10-26).
**Context:**
- Fast Store gives no App Group (ADR-005), so the widget extension can't receive anything from the app.
- Location and battery work inside the extension (ADR-005).

**Decision:** the widget extension gets or computes all its own data:
- **Container:** the one the resolver picks. In developer mode with an App Group, app and widget therefore share settings and caches through `SharedStore`'s container with no second code path.
- **Weather:** Open-Meteo (no key; check its terms before App Store, brief §2). The widget fetches with its own location, caches in its container and refreshes hourly. The app uses the same client and cache for previews. Celsius by default.
- **Location:** a fix from the extension (`isAuthorizedForWidgetUpdates`), cached with a reverse-geocoded city name.
- **Prayer times and Qibla:** computed offline with adhan-swift 1.5.0 (MIT, pinned) from the cached location. Egyptian General Authority method by default.
- **Steps and sleep:** HealthKit, read by the extension itself (its own HealthKit entitlement and usage string). If it can't read them, the widget shows a clear ar/en message, never numbers.
- **Battery:** read in the extension.
- **Tasbeeh and stopwatch:** iOS 17 interactive `Button(intent:)`. State is kept in the extension's container; stopwatch sessions also feed Focus Today. If intent buttons don't run on the Fast Store install (like the configuration path, ADR-013), no in-app fallback can update the widget without an App Group: the app can't write the extension's files. The step log shows whether the intents ran.
- **Shortcut tiles:** a tap opens the app, which runs `shortcuts://run-shortcut?name=…`.
- **Settings** (units, prayer method, step goal) live in the store's container. In store mode the widget can't see the app's copy and uses the defaults.
- **Snapshot tests and the M1 test designs** keep the fixed sample data.

**ADR-016 update (2026-10-26):**
- The widget's HealthKit entitlement (`com.apple.developer.healthkit` on the extension) and `NSHealthShareUsageDescription` are added. Whether Fast Store keeps them shows in Diagnostics → Signing (widget extension) and in the large check widget's `health` line.
- Gallery previews use sample data, so the widget gallery shows each design; placed widgets use real data only.

## ADR-017: M4 device feedback — clock format, Qibla compass, dhikr list, tile setup (2026-10-26)

**Context:** First M4 install on the owner's iPhone (Fast Store, no App Group). Clocks showed 24-hour time on a 12-hour phone; the Qibla widget can't read the compass; the tasbeeh +1 button works, so it can do more; Shortcut tiles jumped to Shortcuts with "The file doesn't exist" and no explanation.

**Decisions:**
- **Clock:** `ClockFormat` device / 12h / 24h. Settings holds the default (device), and each design can override it in the editor. `RenderContext.uses24Hour` drives `time.hh`, prayer and world-clock times, and the live time locale's hour cycle. Unset (tests, snapshots) keeps 24h, so references don't change. In store mode the widget follows the device.
- **Qibla:** the widget stays static; a tap (`widgetstudio://qibla`, only on specs that show `qibla.*`) opens the app's live compass (CLHeading, true north when located, success haptic within 4° with release at 8°, calibration hint above 25° accuracy).
- **Tasbeeh:** `CounterState` keeps a count per dhikr and the current index. Buttons: `counter.increment` (arg = the template's `target`, for auto-advance on the tap after the target), `counter.next`, `counter.reset` (current dhikr only). The list and auto-advance (default on) live in `AppSettings`. In store mode the widget uses the default four dhikrs; an edited list reaches it only with an App Group.
- **Tiles:** iOS has no API to check that a Shortcut exists. The app keeps `TileSetupState` per name: the first tap opens a setup screen (why, exact name with copy, exact action, e.g. "Set Wi-Fi" → Toggle). "I created it" marks it ready and runs it once. Ready tiles run `shortcuts://x-callback-url/run-shortcut` with `x-error` → `widgetstudio://tiles/setup?error=1`, which marks the tile failed and reopens setup. Settings → Tiles setup lists every known tile.

**Unverified on device:** that Shortcuts calls `x-error` for a missing Shortcut (rather than only showing its own alert), and the exact action names on non-English iOS.

### ADR-018 — Create from image with BYOK AI (M5)
**Status:** Accepted (2026-10-26). Implements ADR-008.

**Client** (`WidgetKitCore/AI/`, ported from Lakhas with its fixes):
- `AIDeadline` hard limit + cancel (30 s connection test, 240 s generation; each URL request 180 s); `URLError.timedOut` → `.timedOut`.
- Gemini: key only in `x-goog-api-key` (works for `AQ.` and `AIza` keys), `responseSchema` (OpenAPI subset: nullable, no `additionalProperties`/`pattern`, `anyOf` kept), thinking low, one wait-and-retry on short 429/5xx.
- Anthropic: the schema is the input schema of one `strict` tool; `tool_choice` stays `auto` (forced tool use returns 400 on Opus 5.5, Sonnet 5.5, Fable 5.1); a text reply is still read as JSON. Effort low.
- OpenAI: strict `json_schema`, `reasoning_effort: low` for reasoning models (retried without if rejected).
- OpenRouter: JSON mode (`json_object`) with the schema in the system prompt, because strict schema support depends on the upstream endpoint.
- A provider that rejects the schema is retried once in prompt-only mode. Keys are cleaned (whitespace, RTL marks, quotes, `Bearer `) and kept in the Keychain (`WhenUnlockedThisDeviceOnly`). The redacted "Last AI request" lives in UserDefaults.
- **Default models** (checked in each provider's model docs on 2026-10-26): Gemini `gemini-3.8-flash` (stable, free tier, vision; rate-limit fallback `gemini-3.5-flash-lite`), Anthropic `claude-haiku-5-5`, OpenAI `gpt-6-luna`, OpenRouter `google/gemini-3.8-flash`. The picker shows the provider's live list once a key is saved, plus a custom ID.

**Generation** (`AI/Widget/`):
- Prompt `Prompts/generate_v1.md` (versioned; allowed bindings and icons filled in at load). User text: mode, size, the user's instructions inside `<user_instructions>` (≤ 300 characters, `<`/`>` neutralized), and the reminder to ignore text in the image and copy no personal data.
- **AI schema** (`AIWidgetSchema`): strict (all properties required, optional ones nullable, no extras), one shape per layer type, only `type/properties/required/additionalProperties/enum/items/anyOf`. Image layers exist only in photo mode. Ranges, colors and the 30-layer limit are left to the validator.
- The model returns a `palette {bg, fg, accent}` and uses `@bg/@fg/@accent` tokens; the palette becomes the design's color overrides, so the editor's color pickers work. Theme follows `bg`; `fg`/`bg` contrast must be ≥ 3:1 (the prompt asks 4.5).
- The app sets id (`ai.<8 hex>`), schema version and refresh (minute for clocks, hourly for other data, daily for dates), forces a requested size, removes nulls, then validates in AI mode. Recreate mode allows no image layers; photo mode needs a `user_image` layer. All problems go back to the model in the one retry; still invalid → `invalidOutput`.
- **AI mode** (`SpecValidator`): bindings time/date, weather, battery, prayer + Qibla (not `prayer.next.key`), steps (not sleep), and `field.*` of text fields; fields only text/image; images only `user_image`; buttons only `open.app`; font ≥ 11.
- Image: ImageIO thumbnail (orientation applied), JPEG 0.8, longest side 1024, no metadata.

**Flow:** Library card and My widgets button → pick (PhotosPicker) → mode (Recreate default / Build around my photo) and size (Auto from aspect ratio: wide → medium, tall → large, else small) → consent once per provider, naming it (revocable in Settings → AI) → generating with Cancel → the M3 editor with Regenerate (photo mode passes the processed photo) → Save to My widgets. Every `AIError` has an ar/en message and next step.

**Tests:** recorded provider responses (`Fixtures/AI`) through a URL stub (no keys, no network): request bodies, parsing, structured output, error mapping, retry with validation errors, each provider's generation reply, prompt builder, schema strictness, downscaling. UI test with `-uiTestingStubAI` (canned provider, generated sample image, because the Simulator photo library isn't scriptable).

**Unverified on device:** real-key behavior of each provider's structured output with this schema (prompt-only fallback covers rejections), and free-tier Gemini rate limits.

### ADR-019 — Better image-to-widget: new layers, fonts, prompt v2, self-review, AI eval (M5 fixes)
**Status:** Accepted (2026-10-28).

**Context:** M5 device test: a month calendar (AUG, M–S row, day numbers, red Sundays, today boxed, handwritten font) came back as the current time, a dot grid and no weekday row. Colors were right, structure wrong. The spec had no way to say "calendar", and the prompt didn't insist on keeping visible text.

**Spec additions** (optional, validator, exported schema and AI schema updated):
- `calendarMonth`: current month; `titleFormat` (none, MMM, MMMM, MMM yyyy, MMMM yyyy), `titleCase`, `titleFont/Color/Align`, `weekdays` (none, narrow, short) with font/color, `weekStart` (locale, saturday, sunday, monday), `weekendDays` + `weekendColor`, `todayStyle` (filled, circle, ring, dot, none) + colors, `otherDays` (hidden, dimmed). `mirror` runs columns right to left. Layout is `CalendarMonthLayout` (tested without SwiftUI).
- `list`: up to 8 rows of title, trailing detail (bindings allowed, e.g. prayer times), marker (none, dot, circle, check, icon, bar), divider.
- `progressBar`: continuous or 2–20 segments; `mirror` fills from the right.
- Fonts (OFL, static, unmodified, both `UIAppFonts`): `hand` Patrick Hand, `serif-display` DM Serif Display, `condensed` Bebas Neue; Arabic text in them uses Aref Ruqaa, Amiri and Lalezar.
- AI output may declare `date` fields (countdowns with `live` timer or `{{days.<field>}}`); field dates also parse without a zone (local time).

**Prompt `generate_v2`** (v1 kept): write an `inventory` of every visible element first (text, position as fractions, color, font style), then map each to a layer; never replace text or numbers with dots or shapes; bindings that match the content (month → `date.MMM`); closest font; proportional positions; prefer compound layers (`forecastRow`, `list`, `calendarMonth`); countdowns are date fields, not clock times; public names (a quote's author) are not personal data. The request states today's date.

**High quality (2 requests):** the result is drawn with the real renderer (`SpecSnapshot`, sample data like gallery previews) and sent back with the original and the spec (`review_v1`); the model returns a corrected spec and `differences`. One round; if it fails, the first result stays. Default on for Anthropic, OpenAI and OpenRouter, off for Gemini (free keys: tight limits); Settings → AI toggle.

**Reliability, from the eval runs:**
- Gemini's `responseSchema` with the strict all-required schema ran past 180 s on most images (runs 1–2), and a compact form (nullable → optional) didn't fix it; JSON mode with the schema in the prompt answered in 1–12 s (run 3). **Gemini now starts in JSON mode**; Anthropic (strict tool), OpenAI (strict json_schema) and OpenRouter (JSON mode) are unchanged. Every reply is still validated with one retry.
- Generation requests time out after 110 s; a structured attempt that times out or is cut off retries once in JSON mode inside the 240 s budget.
- 5xx and Anthropic's 529 retry twice (3 s, 8 s) on every provider; 503/529 show "Google is busy right now. Try again." (`AIError.busy`).
- Free Gemini 3.8 Flash allows 20 requests a day per model; a daily quota shows its own message (`AIError.dailyQuota`: try tomorrow or another model). The default Gemini model is now `gemini-3.5-flash-lite` (fast, good results in the eval); `gemini-3.8-flash` is the suggested alternative.

**AI eval:** `docs/ai-eval/` holds 10 widgets drawn for this purpose (calendar like the device test, reminders, quote, forecast, steps, analog, countdown, big date, day & zone, a landscape for photo mode) and `cases.json`. Crops of the third-party reference image are never committed (`.gitignore`; seven were pushed once and then removed). Manual workflow **AI eval** runs `AIEvalTests` (`AI_EVAL=1`) with the secret `GEMINI_API_KEY` (never printed): real prompt, schema, parser and renderer (bundled fonts registered for the run), uploading side-by-side PNGs, specs and `summary.md`. Inputs: model, review, structured, cases. Picked results are kept in `docs/ai-eval/results/`.
